Systems S1 · GPU Navier–Stokes

A Navier–Stokes solver on a 4 GB laptop GPU

A from-scratch CUDA solver for two-dimensional incompressible flow. It is verified to machine precision against independent code, exactly second order in space, and validated on the lid-driven cavity. Then it is made 13.5× faster on small grids and about 2.5× on large ones by removing launch latency, moving the multigrid to mixed precision, and blocking the smoother in shared memory, and hardware counters show where the remaining time goes. The answer stays the same throughout, and at times identical to the last bit.

§1The scheme

The equations are the incompressible Navier–Stokes equations in two dimensions,

$$\partial_t \mathbf u + \nabla\!\cdot(\mathbf u \otimes \mathbf u) = -\nabla p + \nu \nabla^2 \mathbf u, \qquad \nabla\!\cdot\mathbf u = 0 .$$

Velocities live on a staggered (MAC) grid[1], with \(u_{i,j}\) on vertical faces, \(v_{i,j}\) on horizontal faces and the pressure at cell centres. On this grid the discrete divergence of a discrete gradient is exactly the 5-point Laplacian, so the projection has no spurious pressure modes. Advection uses the conservative form with central interpolation, second order in space.

Time integration is the three-stage strong-stability-preserving Runge–Kutta scheme of Shu and Osher[3], with a projection after every stage[2],

$$\mathbf u^{(1)} = \mathcal P\big[\mathbf u^n + \Delta t\, L(\mathbf u^n)\big],\quad \mathbf u^{(2)} = \mathcal P\big[\tfrac34\mathbf u^n + \tfrac14(\mathbf u^{(1)} + \Delta t\, L(\mathbf u^{(1)}))\big],\quad \mathbf u^{n+1} = \mathcal P\big[\tfrac13\mathbf u^n + \tfrac23(\mathbf u^{(2)} + \Delta t\, L(\mathbf u^{(2)}))\big],$$

where \(\mathcal P[\mathbf u^*] = \mathbf u^* - \nabla\phi\) with \(\nabla^2\phi = \nabla\!\cdot\mathbf u^*\). The Poisson equation is solved by geometric multigrid V(2,2) cycles: red-black Gauss–Seidel smoothing, full-weighting restriction, bilinear prolongation, down to a 4 × 4 grid[4]. The same templated source compiles to FP64 and FP32.

§2Verification and convergence

Before measuring anything, the GPU code was checked against an independent NumPy implementation of the same discretisation that solves the pressure equation exactly with an FFT, using the eigenvalues of the discrete Laplacian. The two share no code. After the full Taylor–Green run at N = 64, the FP64 GPU velocity field agrees with the NumPy field to · in the max norm, which is machine precision. That checks the advection stencils, the Runge–Kutta stages and the multigrid solve together.

The Taylor–Green vortex[6] has an exact solution on the periodic box,

$$u = \sin x \cos y\, e^{-2\nu t},\qquad v = -\cos x \sin y\, e^{-2\nu t},$$

so the error can be measured directly. With \(\Delta t \propto h\) the Runge–Kutta error is \(O(h^3)\) and stays hidden behind the \(O(h^2)\) spatial error.

§3Multigrid and the FP32 floor

In FP64 each V(2,2) cycle reduces the residual by a factor of 0.053 to 0.059, the same at every grid size from 64 to 2048. That is the grid-independent convergence multigrid theory promises, and the solver reaches a relative residual of 10⁻¹⁴.

FP32 cannot follow. The residual \(r = f - L_h p\) subtracts terms of size \(|p|/h^2\), so its rounding error is about \(\varepsilon_{32}\,|p|/h^2\). It grows as the grid is refined, and the relative residual stalls at a floor that rises from 1.3 × 10⁻⁶ at N = 64 to 5.9 × 10⁻⁵ at N = 2048. With a 10⁻⁵ tolerance the FP32 solver never converges on large grids and runs to its 40-cycle cap, which makes it slower than FP64 (157 against 33 ms per step at N = 128), not faster.

§4Where the time went

The first timing run gave a clear picture. In FP64 the pressure projection took 96 to 99% of every step, and a V-cycle cost 1.3 to 2.2 ms whether the grid had 64² or 512² cells. A cost that does not grow with the problem is not arithmetic. Each cycle launched hundreds of tiny kernels, 120 for the 4 × 4 coarse solve alone, and every convergence check copied a reduction back to the host and waited for it.

Meanwhile the FP32 advection kernel already ran at 98.9 GB/s, 95% of the measured copy bandwidth, so the stencil code itself was fine. The FP64 version stalled near 42 GB/s. By my hand count of about 55 to 60 operations per cell that is roughly 75 GFLOP/s, the same order as this card's FP64 peak. The hardware counters in §8 later confirmed that the kernel is compute bound, but measured 51 GFLOP/s, because my count was too high.

Each fix below is a command-line switch, so it can be measured on its own. They are added in order.

The single-launch coarse solve and CUDA Graph capture remove most of the cost on small grids. On large grids the solver is bandwidth bound and the gains come from moving fewer bytes, first by mixed precision and then, in §7, by the blocked smoother.

§5Mixed-precision multigrid

The FP32 floor in §3 comes from computing the residual in low precision, not from smoothing in it. So the iterate and its residual are kept in FP64, and only the correction is computed in FP32, one V-cycle per outer iteration,

$$r_k = f - L_h p_k \;\;(\text{FP64}),\qquad L_h e_k \approx r_k \;\;(\text{one FP32 V-cycle}),\qquad p_{k+1} = p_k + e_k \;\;(\text{FP64}).$$

This is iterative refinement in the sense of Higham and Mary[7]. One V-cycle only needs to reduce the error by about 0.06, which FP32 does comfortably, so the outer iteration inherits the FP64 contraction rate (Figure 2). On Taylor–Green the mixed solver reproduces every FP64 error digit at every grid size from 32 to 1024, and runs 1.38 to 1.44× faster because the smoother moves half the bytes.

§6Walls: the lid-driven cavity

The periodic box has no boundaries, so it cannot test the hardest part of most real flows. The cavity solver adds walls to the same scheme. Tangential no-slip is imposed through ghost values, \(u_{\text{ghost}} = 2U_{\text{wall}} - u_{\text{inside}}\), the lid moves at \(U = 1\), and the multigrid stencil drops neighbours outside the domain, which imposes the homogeneous Neumann condition the pressure correction needs. Each case runs until \(\max|\partial_t u| < 10^{-7}\).

The comparison is against the tables of Ghia, Ghia and Shin[5]. The publisher's copy could not be fetched automatically, so the values were taken from three independent reproductions and cross-checked value by value. The Re = 100 and Re = 1000 columns agree in every source.

How to read the comparison

The solver converges on itself at second order. Between successive grids the centreline profiles change by 1.1 × 10⁻³ and then 2.6 × 10⁻⁴ at Re = 100 (observed order 2.11), and by 2.3 × 10⁻² and then 6.2 × 10⁻³ at Re = 1000 (order 1.88). At Re = 100 the remaining difference from Ghia, about 0.005 in u and 0.009 in v, does not shrink with refinement, so it is larger than this solver's own discretisation error. Ghia's values come from a 129 × 129 grid and carry discretisation error of their own, so this comparison cannot assign the residual difference to either side. Settling it needs a higher-accuracy reference. That is listed below as open work, not claimed.

§7A race in the fast smoother

On large grids every smoothing sweep reads and writes the whole fine grid, and red-black ordering doubles that. The blocked smoother loads a 32 × 32 tile with a 4-cell halo into shared memory and performs all four half-sweeps of a smoothing call there. The valid region shrinks by one cell per half-sweep, which is why the halo is four cells wide. The fine grid is then touched once per call instead of four times.

The first version wrote the tile back in place, and it was wrong. Its results differed from the unblocked smoother only at N = 2048, in the second significant digit of the residual history.

// block A                                   block B (neighbour, scheduled later)
load tile + halo from p      // old values
4 half-sweeps in shared memory
write interior back to p     // p now partly new
                                             load tile + halo from p   // halo already updated by A

A block's halo belongs to its neighbours' interiors. When all blocks fit on the GPU at once, as they do on small grids, every block finishes loading before any block writes, and the bug cannot show. At N = 2048 the 4,096 blocks run in waves, so later blocks read values that are already one smoothing call ahead. The fix writes to a second buffer and swaps the pointers. Each level is smoothed exactly twice per V-cycle, so the pointers return to their original buffers after every cycle and the captured CUDA Graph stays valid. After the fix, the full Taylor–Green solution is bitwise identical to the unblocked solver at N = 512 in FP64 and at N = 1024 in mixed precision.

Table 2. ms per time step, median of 5. The blocked smoother is applied only to levels with N ≥ 512.

Below N = 512 whole time steps got slower with the blocked smoother (5.39 → 7.14 ms at N = 256). The counters in §8 explain it. At N = 256 the blocked kernel launches only 64 blocks, about one wave on this GPU's 20 SMs, and on the next level down 16 blocks fill a quarter of a wave. Each block also recomputes its halo, which is a large share of a small tile. The switch therefore stays off below N = 512.

§8What the hardware counters say

Timings say how long a kernel takes, not why. Nsight Compute reads the GPU's own counters for every kernel, including the bytes moved to and from memory, floating-point instructions by type, and how busy each execution pipe was. Placing each kernel on a roofline[9] shows which limit it is pressing against. Every kernel below is profiled on its finest level at N = 1024.

The ceilings are measured rather than copied from a datasheet. The profiler locks the SM clock at · GHz. On the busiest FP64 kernel the FP64 pipe was active for exactly · cycles per warp instruction, so each of the 20 SMs retires two FP64 lanes per cycle. That gives

$$P_{64} = 20 \times 2 \times f_{\text{SM}} = 48.3\ \text{G instr/s},\qquad 96.6\ \text{GFLOP/s if every instruction is an FMA}.$$

Memory bandwidth from the memory clock and bus width is · GB/s. The profiler's own percentages imply · GB/s, which agrees.

Figure 6. Each point is one kernel. A point on the sloped line is limited by memory bandwidth, and a point under a flat line by arithmetic. The FP32 peak is computed from the lane count and lies far to the right, so every FP32 kernel is memory bound by a wide margin.

Three readings

Almost everything is memory bound and already near the limit. Every streaming kernel, in both precisions, moves data at 91 to 95% of peak bandwidth. Speed for these kernels can only come from moving fewer bytes, which is what mixed precision and the blocked smoother do.

The FP64 right-hand side is compute bound. At 1.6 FLOP per byte it sits right of the FP64 ridge, reaching 51 GFLOP/s with the FP64 pipe busy 84% of the time. Only 24% of its FP64 instructions are fused multiply-adds, so its practical ceiling is about 60 GFLOP/s, not 96.6. This settles the estimate in §4.

The blocked smoother was wasting half its arithmetic. Its FP64 pipe was 82% busy, yet it delivered only 20 GFLOP/s. The cause was divergence. The red-black update skipped cells of the other colour with a branch, so on each FP64 instruction only 13.8 of a warp's 32 lanes did work while the pipe stayed busy issuing them. The fix assigns each thread a cell of the current colour directly. The arithmetic and the update order are unchanged, so the solution stays bitwise identical, checked byte for byte at N = 512 in FP64 and N = 1024 in mixed precision.

§9Running in your browser

The flow behind the homepage headline is this solver, ported to WebGPU compute shaders: the same MAC grid, conservative advection and multigrid V(2,2), with a single-workgroup coarse solve, on a 256 × 128 periodic grid in 190 dispatches per frame. It differs from the CUDA code in ways the homepage states: FP32, Heun's method instead of SSP-RK3, a fixed two V-cycles per projection warm-started from the previous pressure, linear drag, and a passive dye advected semi-Lagrangian for display. The divergence of the displayed field is read back asynchronously and printed live. On the development laptop it holds 60 fps, the display limit, with \(\max|\nabla\!\cdot\mathbf u| \approx 3\times10^{-4}\). Browsers without WebGPU fall back to a simpler CPU solver[8].

§10Limitations and next steps

All timings come from one laptop GPU whose clocks vary with temperature. Medians of five repeats are reported, and the spread is under 4% in the ablation, but other hardware will differ. The profiler locks the clock at its base value, so rates in §8 are lower than the timings elsewhere on this page. The ratios between kernels are what the analysis relies on. The cavity comparison needs a higher-accuracy reference to decide the residual difference from Ghia. The divergence found in §8 leads into systems study S2, the anatomy of GPU computation, which studies effects like it in isolation.
